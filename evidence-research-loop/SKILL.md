# 证据驱动的方案进化

把开放问题转成一个实际运行的搜索过程：

**定义 solution → 冻结裁判 → 建立基线与多种候选 → 运行并归档 → 依据失败产生下一代 → 保留精英与多样性 → 冻结 → 独立测试和消融 → 交付可复核结论。**

这套方法提取 ShinkaEvolve 的程序进化内核，并补上工程研究所需的需求边界、独立测试和证据管理。它可以优化代码、软件架构、Agent 工作流、算法、配置、业务流程或仿真设计。它找到的是**在已声明搜索空间、裁判、数据和预算下实测最好的方案**；除非完成穷举或形式证明，不得称为全局最优。

## Codex / Cursor 执行入口（Skill-only）

Cursor 和 Codex 读取本 Skill 后直接运行 `scripts/`，不经过 MCP。不要调用 `evidence-research-loop-local` 或其他 ERL MCP 工具。详细命令见 [Skill-only 执行](references/cursor-skill-only.md)。

1. 把任务建在项目目录；
2. 用 `scripts/evolution_controller.py` 做 `scaffold / validate / start / resume / status / export`；
3. 用 `scripts/audit_search.py` 做独立审计；
4. Research Graph、Composition Graph、Scientist Runtime 同样直接调用对应脚本；
5. 需要 AI 生成候选时设置 `generator.backend=codex`，在用户本机环境运行，以便使用已有 Codex 登录；
6. 启动付费或账户计量模型前，先报告模型、最大调用数、单次超时、总时限和费用是否可知；
7. **每次搜索都做进度 Canvas**，规范见 [进度 Canvas](references/progress-canvas.md)。开始前先立看板，结束后用实测数字更新；聊天旁打开，并在任务目录留下 `progress.canvas.tsx` 以便进 Git。缺少进度看板不得声称本轮已向用户交付。

仓库内同时放置 `.cursor/skills/evidence-research-loop/` 和 `.codex/skills/evidence-research-loop/`。不得把 Token 写入 `task.json`。MCP 服务器源码可以保留在发布包中，但不是这条执行路径的一部分。

## 先选择工作模式

- **工程方案进化**：用户要开发软件/系统、找最佳实现、优化性能或把 ShinkaEvolve 原理迁移到其他领域。读取 [工程方案进化](references/engineering-evolution.md)。
- **Research Graph 协作**：一个方案内部需要多个 Agent 分解依赖、并行完成节点，或在失败后重构蓝图。读取 [Research Graph](references/research-graph.md)。它管理任务调度；`dependencies` 本身不是经验证的组合关系。
- **Composition Graph 组合验收**：同一目标有多条实现路径，需要分别验证子能力、组合关系和实际系统，并保存可跨项目复核的资产。读取 [Composition Graph](references/composition-graph.md)。它区分条件组合通过与整体接受，不替代外层搜索，也不把工程测试提升为数学证明。
- **研究结论比较**：用户要检验假设、比较干预或复现实证结果。按本文流程执行。
- **Scientist Mode**：用户要形成假设、查文献和新颖性、管理多分支实验、生成科学分析与论文评审，或搭建 AI Scientist-v2 式流程。读取 [Scientist Mode](references/scientist-mode.md)，用 `scripts/scientist_runtime.py` 执行真实 stage command；复杂实验树可组合 Research Graph。五模块是可选产品设计，其真实效用必须在目标任务上另行比较，结构模板和单元测试不能提供该证据。
- 两者重叠时，以可运行系统为候选、以研究协议管理证据；模块微基准不能替代端到端系统验收。
- 涉及本用户员工年度目标系统时，另读 [KPI 研究约束](references/kpi-goals.md)。

开始或恢复时读取 [研究记录](references/research-record.md)，核对已有协议、候选、原始结果和测试访问历史。接续有效工作，不把旧实验冒充新问题的证据。

需求改变时建立新版本协议，并把上一版本冻结赢家作为新 baseline。若新要求使它预期无法通过，在任务中显式设置 `selection.allow_failing_baseline: true`；保留该失败作为需求差距证据，候选必须通过新硬门禁后才能入选。不要先手工把旧实现修到通过再称为研究器续作。

项目没有现成搜索控制器时，按任务选择执行器，全部在本机 Skill 脚本中运行：外层多代候选搜索用 `scripts/evolution_controller.py`；内层多 Agent 节点协作用 `scripts/research_graph.py`；真实科研五阶段用 `scripts/scientist_runtime.py`。先读 [Skill-only 执行](references/cursor-skill-only.md)、[自动搜索与任务适配](references/automatic-search.md)、[Research Graph](references/research-graph.md) 或 [Scientist Mode](references/scientist-mode.md)。Cursor/Codex 项目不要改用 MCP。旧 `assets/task-templates/scientist-mode` 仅用于兼容性冒烟，不得拿它的预设分数声称科研能力；正式 Scientist 项目必须创建 `research-plan.json` 并接入真实 stage adapter。启动真实模型前，先向用户报告模型、最大调用数、单次超时、总时限和可计算费用；价格未知时明确记录 `unknown` 并以调用数和时间硬停止。

Research Graph 的使用顺序是：冻结 blueprint、每个节点的 `output_contract`、verifier 及其 `frozen_files` → 多 worker 原子 `claim` → 定期 `heartbeat` → 只向 worker 提供直接依赖资产 → 生成产物 → `execute` 真实 verifier → 登记 verified asset 与 contribution。节点失败必须先 `fail` 留证，再用新的 blueprint revision 做 split/rewire/supersede/invalidate；依赖变化的下游证据作废。资产复用必须同时匹配 statement、直接依赖资产、输出契约、verifier 契约和 scope，不能只比较输出形状。每项贡献记录人/Agent/模型、角色、来源、费用、耗时、产物哈希与验证结果；该账本用于追溯，不自动决定署名、IP 或绩效。

Scientist Runtime 的使用顺序是：冻结 `research-plan.json` 和输入 → `validate` → `start/resume` 实际运行 ideation、literature、experiment、analysis、review command → `audit` → `export`。stage adapter 在契约上只应读取 `{request}`、声明的冻结输入和直接证据，并向 `{response}` 写出 JSON；当前 command backend 不是完整 OS 沙箱，运行不受信任代码时必须另加独立容器、最小挂载和网络限制。实验原始证据必须保存在本次 attempt 目录并被 `evidence_files` 引用。没有来源不能声称新颖，没有验证过的实验文件不能支持经验主张，独立评审必须逐项接受 required claim。必须同时报告执行是否完成、审计是否有效、研究包是否接受；三者不得混用。

自动控制器把父代、公开任务说明和开发反馈复制到独立 generator workspace；裁判、契约内部和 holdout 不复制进去。`codex` 后端把允许内容嵌入请求，在 `read-only` sandbox 中返回完整候选文本，由控制器校验后落盘；需要操作系统级读取隔离时使用固定镜像 ID 的 `docker-command` 后端，只挂载 generator workspace。不能把提示词中的“不要访问”当成隔离证据。

控制器在调用前持久化 request 和 `generation_started`，调用完成以哈希链事件作为计数提交记录，再由事件重建状态快照。恢复入口会先消费已完整落盘的调用结果，再判断能否发起新调用；已开始但结果未知的调用标为 `generation_abandoned_unknown_outcome`，不会自动重试和重复计费。搜索以硬门禁过滤，维护精英、Pareto、机制 niche、失败和行为相似档案，达到轮次、调用、时间、费用或无改进条件后冻结并运行 holdout。源码完全重复不再次评测；行为相似会记录成组供选择与报告使用。

`max_wall_time_sec` 是基线初始化完成后的搜索硬时限，覆盖生成、开发评测、冻结和最终 holdout；一次性的协议建立和基线校准不计入该值。外部进程按剩余时限设置 timeout，并预留控制器落盘余量；超时时必须终止并回收整个后代进程树，Windows 使用 Job Object，POSIX 使用独立进程组。时限耗尽且冻结矩阵未完成时，状态必须是 `holdout_incomplete`，审计必须失败，不能宣布完成。`completed` 只表示预期的候选 × 重复次数全部存在终态且全部通过硬门禁；终态齐全但有硬门禁失败时使用 `completed_with_holdout_failures`。

holdout 在 `run.json` 和访问开始记录落盘后中断时，必须保留该次尝试，并把它登记为 `interrupted` 终态；恢复创建新的 run ID，显式记录 `retry_of_run_ids` / `retried_by_run_id`。审计只把带控制器事件、访问事件和重试关联的中断记录视为合法终止证据，并只用完整评测填充冻结矩阵。不得删除旧失败记录来取得通过状态。

只需人工登记或项目已有自己的优化器时，可单独使用 `scripts/solution_evolver.py` 的 `init / lock / register / run / rank / freeze / status`。编辑契约和裁判后必须先 `lock`；每次 `run` 会校验研究器、契约、候选、冻结输入及声明的 Docker/Git/命令身份。项目已有 MLflow、数据库或竞赛框架时可沿用现有系统，不强制迁移。

## 1. 定义 solution 和搜索边界

先记录用户要做的决定，而不是先生成方案。最少明确：

- 输入、输出、使用者和运行环境；
- 可修改区域与不得改变的接口/约束；
- 候选的可执行形态，例如代码分支、配置、算法函数、工作流定义或可仿真设计；
- 硬性门槛、优化目标、资源成本和严重错误；
- 什么结果会推翻当前方向；
- 开发预算、候选数/轮次、停止条件和最终生产门禁。

如果目标是“做一个好软件”，先产出最小端到端骨架和验收接口。只比较提示词、孤立函数或设计文档时，只能声称该组件的结果。

## 2. 查证据并形成机制不同的候选

- 优先查论文、官方实现、标准和公开基准；区分实证证据、工作流程、教学样例和宣传材料。
- 将证据转成“依据 → 机制假设 → 可执行改动 → 预期指标 → 失败判据”。
- 保留一个合理简单基线，并建立至少两个机制不同的候选。差异必须改变系统行为，不能只是改名、改写说明或生成更复杂但等价的代码。
- 记录候选 ID、父方案、作者/模型、机制、来源、实现哈希、预计成本和淘汰条件。没有调用外部系统就不要称为外部模型实验。

文献不是成功证据。公开赢家代码可作为正对照或机制来源，但必须标明“复跑公开方案”；不能声称由当前搜索独立发现。

## 3. 在调优前冻结裁判

评估器独立于候选，候选不得读测试答案、修改裁判或自报得分。先完成：

1. 固定输入/输出契约、数据版本、主要指标、比较方法和错误条件；
2. 划分开发集、回归集和独立测试集；独立测试在方案冻结前不得用于提案或选择；
3. 用已知正确、边界和错误候选验证裁判；
4. 保存协议、裁判、数据和基线哈希。

独立测试集还必须在首次执行前做机器可检验的新颖性核对：把拟用 seed、样本 ID、时间窗或来源键与历史协议、run 记录和已揭盲集合求交，保存输入范围、交集和核对脚本的哈希。存在重叠时，该部分只能标为回归复测；另建版本化协议和未使用数据，才能提供新的独立泛化证据。

输入格式是契约的一部分。对解析器、协议适配器和数据管道，先列出实际支持的语法与边界，再用能区分实现的样例测试，例如空输入、转义/分隔符、跨行记录、编码、极值、重复和非法输入。记录分隔符、空白和转义必须遵循目标格式的语义；不要默认宿主语言的 `splitlines`、trim 或 Unicode 分类与目标协议相同。只要有可信参考解析器，就对边界类别做差分测试，并保存“契约能力 → 覆盖样例/性质”的矩阵。有限样例全部通过只能说明该测试集通过，不能外推为兼容整个格式标准。

区分**证据完整性**与**测试充分性**：哈希匹配、重放和独立汇总证明已记录结果可复现，不能证明测试集覆盖了契约。宽泛兼容性主张需要由契约推导的性质测试、边界类别覆盖或差分/模糊测试；否则把结论限定为具名测试和工作负载。

协议锁必须覆盖实际执行链：研究器、候选、契约、裁判、必要依赖、容器镜像身份和相关仓库 commit。只在报告里写哈希不算锁定；执行前和执行后都要重新校验，不一致立即拒绝。每次运行使用新的 run ID 和空结果目录。非零退出、超时、缺失/非法输出或非有限指标一律失败，不能读取前次残留的成功文件。

硬约束先于软目标。多目标问题优先保留目标向量和 Pareto 前沿；只有在业务权衡已确定时才冻结加权总分。安全性、用户体验、可维护性等无法可靠自动评分的维度保留真人评审，不让 LLM 自评分充当事实。

## 4. 运行种群、档案和失败驱动迭代

每一轮实际运行候选并保存原始输出、命令、版本、种子、模型、耗时、费用、退出状态和评分。代码或计划没有运行就不算候选证据。

分别报告唯一问题/数据集数量、候选执行次数和内部计时次数。同一 seed 或同一确定性 workload 的重复运行用于估计运行波动，不得累计成新的独立问题数。

逐例同时保存**实际耗时**和**计分值**。错误答案被赋予的 timeout penalty 只是计分值，不能写成实际运行了同样时长。分位数必须能从逐例记录独立重算；重复比较要报告波动和不确定性，单次消融不能宣称稳定贡献。

使用内置档案器时，在 Solution Contract 的 `evaluator.command` 中用参数数组声明裁判，不拼接 shell 字符串。裁判将硬门禁 JSON 和指标 JSON 写入 `{result_dir}`。`freeze` 只接受已在同一协议锁下通过硬门禁的候选；只有 baseline 也通过当前硬门禁时，才可把它作为 `--comparator`。所有冻结对照都必须来自可行档案，配置的对照数量是上限，不能用失败候选补足。holdout 仅允许冻结比较集访问。holdout 的 `started` 必须在执行前追加并 fsync，失败、重试和新 freeze 版本都不得删除既有历史。

维护三类档案：

- **精英档案**：通过硬约束且在主要目标上领先的候选；
- **多样性档案**：机制、架构或行为签名不同的可行候选，防止过早收敛；
- **失败档案**：编译、正确性、性能、资源、集成和泛化失败，保留触发输入及错误类别。

父方案从精英和有价值的多样性候选中选择。下一代可以做局部修补、机制替换、两个父方案的兼容组合或从失败回退；每个子代只引入可解释的主要变化。用代码哈希加行为签名去重：实现不同但输出、路径和指标等价的候选不得反复消耗预算。

按“失败证据 → 原因假设 → 改动 → 新版本 → 重评”记录迭代。裁判或数据有缺陷时保留旧结果，发布协议修订，并把已经看过的测试数据降级为回归集。不得为了制造赢家移动门槛。

达到预先声明的轮次、费用、时间或无改进停止条件后冻结。无改进时接受基线或“当前预算未找到收益”，不无限重试。

## 5. 冻结后做独立测试、消融和压力测试

- 冻结入围规则、候选、参数、裁判和数据哈希后，才运行独立测试。
- 用相同资源限制比较基线、入围候选和必要正对照；报告质量、严重错误、失败率、延迟/资源和实际成本。
- 对声称有效的机制逐项消融，其余条件保持可比。整体方案获益不等于每个组件有效。
- 软件系统按风险增加集成、并发、故障注入、兼容性、回滚或安全检查；这些仍须在协议中事先定义。
- 测试揭盲后若继续修改，保留本轮失败，并建立新的独立测试轮次。

## 6. 沉淀可迁移机制

把最终结果拆成三层：

1. **领域结果**：这个任务上哪个候选实测最好；
2. **机制证据**：哪些设计通过消融显示有贡献；
3. **迁移规则**：迁移到另一领域时，需要重新定义哪些输入、裁判、约束和数据。

不要直接复制赢家代码到另一个领域。可迁移的是搜索契约、档案策略、失败分类和已经验证的机制假设。新领域必须重新建立基线和独立测试。

## 完成条件

只有以下证据齐全，才可称“完成本轮方案进化”：

- 至少一个合理基线和两个机制不同的候选实际执行；
- 冻结裁判统一评分，候选谱系、全部失败和资源成本可追溯；
- 至少一轮由失败或指标差距驱动的改进，或有明确的无改进停止证据；
- 冻结后完成独立测试和相关消融；
- 报告说明比较了什么、实际结果、推荐、未知项、缺少项及数据性质；
- 进度 Canvas 已用最终状态、谱系、分数和 token 用量更新（见 [进度 Canvas](references/progress-canvas.md)）。

用户明确只要求某阶段时，报告该阶段完成即可。工具、依赖或预算受阻时保留成果并标记 `partial/blocked`；无需用户输入即可继续时继续执行。生产部署、真实订单、对外发布或不可逆操作仍遵循原任务授权，研究胜出本身不等于自动上线授权。
