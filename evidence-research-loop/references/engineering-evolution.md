# 工程方案进化

用于软件、系统、算法、Agent、配置、工作流或可仿真工程设计。目标是把“找最好的 solution”变成可重复运行的搜索，而不是让模型一次性给出它认为最好的答案。

## 一、Solution Contract

每轮开始先写一个短契约：

| 字段 | 含义 | 软件示例 |
|---|---|---|
| artifact | 被进化的可运行产物 | Git worktree、服务、函数、配置、工作流 JSON |
| stable interface | 各候选必须保持的接口 | HTTP API、CLI、函数签名、数据库 schema |
| mutable boundary | 允许改变的范围 | 一个模块、算法层、架构组合、部署参数 |
| workload | 统一输入与负载 | 固定测试、trace、数据集、用户任务 |
| hard gates | 一票否决项 | 正确性、安全、兼容、SLA、预算上限 |
| objective vector | 在合格候选中优化的量 | 延迟、吞吐、成本、质量、复杂度 |
| resource envelope | 每个候选可用资源 | 时间、模型调用、CPU/GPU、依赖 |
| behavior signature | 行为去重依据 | 输出摘要、调用图、性能桶、测试覆盖 |
| holdout | 冻结后才可访问的工作负载 | 新时间段、新客户、新 seed、隐藏测试 |

如果无法给出 artifact、workload 和 hard gates，先做需求澄清或原型测量；此时不能声称开始了最优方案搜索。

## 二、按问题选择候选形态

### 代码/算法进化

- 候选是可编译、可测试的代码快照；尽量限制可变模块并保持公共接口。
- 裁判运行正确性测试、微基准和端到端基准。编译失败、测试失败和超时全部入档。
- 性能测量应预热、重复并报告分布；候选不得修改基准。

### 软件架构进化

- 候选必须落成最小可运行切片，不能只比较架构图或文字意见。
- 同一业务场景下比较端到端行为。模块指标仅用于诊断。
- 可变维度可以是存储、缓存、队列、并发模型或服务边界；一次子代优先改变一个主要机制。

### Agent/工作流进化

- 候选是可执行 workflow、工具策略、提示或路由配置。
- 固定任务集、模型版本、工具权限和调用预算；保存完整 trace。
- 同一案例改写不算新的独立样本。LLM 评分只能作为辅助代理。

### 参数与基础设施进化

- 候选是声明式配置；校验范围、类型、依赖与回滚路径。
- 对资源成本、吞吐、尾延迟和故障恢复做联合测量。
- 不在生产环境无界探索；先使用测试环境、回放或仿真。

### 非软件领域

- 需要可执行仿真、实验装置或可靠的人工协议。
- 不能可靠测量的目标保持未知；不要用模型偏好替代真实效果。

## 三、候选生成机制

第一代至少覆盖三种角色：

1. **保守改进**：在基线上修复已知瓶颈；
2. **机制替换**：采用结构上不同的算法或架构；
3. **探索候选**：高不确定但可能跨越当前局部最优。

后续子代来自：

- mutate：对一个父方案做单机制变化；
- repair：针对具体失败输入修复；
- crossover：只组合接口兼容、贡献互补的机制；
- simplify：在保持指标的前提下降低复杂度或成本；
- stress-directed：依据压力测试瓶颈改变实现。

每个候选先写一句可推翻的机制假设。候选生成者可以读开发结果和失败档案，不能读独立测试答案。

## 四、档案与选择

不要只保留一个最高总分。维护：

- hard-pass 精英；
- Pareto 前沿，例如质量/延迟/成本互不支配的候选；
- 每个机制 niche 中的代表；
- 失败类别的最小复现和最近修复；
- 基线与公开正对照。

父代选择兼顾 exploitation 与 exploration：多数预算给当前可行前沿，少量预算给表现不足但机制新颖的候选。新颖性必须由结构差异或行为签名支持；单纯代码改写不算新颖。

推荐选择顺序：

1. 淘汰违反 hard gates 的候选；
2. 对合格候选更新 Pareto 前沿；
3. 在同一 niche 内用主要指标、稳定性和成本排序；
4. 用冻结的业务权衡选最终入围，不在看到测试结果后改权重。

## 五、软件裁判的最小层级

按任务裁剪，但保留端到端层：

1. build/static：编译、类型、lint、依赖契约；
2. correctness：单元、属性、差分或形式检查；
3. integration：真实接口与数据流；
4. performance：代表性 workload 下的分布和资源；
5. resilience：错误输入、并发、依赖故障、恢复；
6. human review：无法程序化的可用性、可维护性或领域风险；
7. holdout：冻结后的新实例/新时间段。

裁判输出至少包含：hard-pass、目标向量、失败类别、行为签名、耗时/费用和原始证据路径。若使用单一 `combined_score`，同时保留未压缩的原始指标。

## 六、与 ShinkaEvolve 原理的对应

| ShinkaEvolve 机制 | 通用工程实现 |
|---|---|
| program population | 多个可运行候选及其谱系 |
| mutation/crossover | 局部改动、机制替换与兼容组合 |
| archive/islands | 精英、Pareto 与机制 niche 档案 |
| verifier/fitness | 冻结的测试、基准、约束和成本 |
| novelty rejection | 代码哈希 + 行为签名去重 |
| adaptive selection | 按实际收益/成本分配下一轮预算 |
| textual feedback | 结构化失败证据驱动 repair |

本 skill 额外要求独立测试、数据泄漏记录、消融和真实工程门禁，使搜索结果可以被审查和迁移。

## 七、停止与交付

达到任一条件停止当前轮：预算耗尽；连续若干候选无 Pareto 改进；只剩不可自动判断的目标；需要新外部数据；或入围方案已达到冻结门槛。停止不是失败，也不证明全局最优。

最终交付：可运行赢家、保留的备选/Pareto 前沿、基线对照、失败档案、冻结记录、独立测试、消融、复现命令，以及上线前仍需的人类决定。生产部署是单独步骤。
