## 1. Freeze local candidate and variables

Run from the `mcp-server-v1` directory after all local tests and Docker smoke
tests pass:

```powershell
$Subscription = '9069dbca-8580-437f-8cac-294d94584d02'
$ResourceGroup = 'lmyrg'
$RegistryName = 'erlmcpacr'
$Registry = 'erlmcpacr.azurecr.io'
$Repository = 'evidence-research-loop-mcp'
$App = 'evidence-research-loop-mcp'
$Endpoint = 'https://evidence-research-loop-mcp.nicetree-1d19d2fd.eastus.azurecontainerapps.io/mcp'
$Tag = '1.1.1-v2.5.1-20261026'
$RevisionSuffix = 'v250-20261026'
$RollbackImage = az containerapp show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --query 'properties.template.containers[0].image' -o tsv
$RollbackRevision = az containerapp show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --query 'properties.latestReadyRevisionName' -o tsv

if ($RollbackImage -ne 'erlmcpacr.azurecr.io/evidence-research-loop-mcp@sha256:3a06637f0cb088a931340a8fee9390a0ae8c0f745796743e3058c714b69854b4') {
  throw "Live rollback image changed since planning: $RollbackImage"
}
```

Use a unique version tag for traceability, but deploy the resolved digest. Do
not update `latest` before acceptance, and never deploy a mutable tag.

## 2. Build in ACR and resolve the immutable digest

```powershell
az acr build --subscription $Subscription --registry $RegistryName `
  --image "${Repository}:${Tag}" --file .\Dockerfile .

$Digest = az acr repository show --subscription $Subscription `
  --name $RegistryName --image "${Repository}:${Tag}" `
  --query digest -o tsv

if ($Digest -notmatch '^sha256:[0-9a-f]{64}$') {
  throw "ACR did not return an immutable digest: $Digest"
}
$LockedImage = "${Registry}/${Repository}@${Digest}"
```

Record the ACR build run ID, tag and digest. A local image ID is useful build
evidence but is not a substitute for the ACR digest that Azure pulls.

## 3. Create a new revision pinned to the digest

The app is already in Single revision mode. Azure keeps the old revision
serving while the new revision provisions, then switches only after readiness.

```powershell
az containerapp update --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --image $LockedImage --revision-suffix $RevisionSuffix

$NewRevision = az containerapp show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --query 'properties.latestRevisionName' -o tsv

az containerapp revision show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App --revision $NewRevision `
  --query '{active:properties.active,health:properties.healthState,provisioning:properties.provisioningState,running:properties.runningState,replicas:properties.replicas}' -o json

az containerapp show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --query '{image:properties.template.containers[0].image,latest:properties.latestRevisionName,ready:properties.latestReadyRevisionName,running:properties.runningStatus,traffic:properties.configuration.ingress.traffic}' -o json
```

Proceed only when `latest == ready == $NewRevision`, the revision is healthy,
the image equals `$LockedImage`, and it has 100% traffic. Do not infer readiness
from `az containerapp update` returning successfully.

## 4. Remote smoke and end-to-end validation

The bearer token stays outside the repository:

```powershell
$Token = [Environment]::GetEnvironmentVariable(
  'EVIDENCE_RESEARCH_LOOP_MCP_TOKEN', 'User')
if ([string]::IsNullOrWhiteSpace($Token)) { throw 'MCP token is unavailable' }

$Health = Invoke-RestMethod -Method Get `
  -Uri 'https://evidence-research-loop-mcp.nicetree-1d19d2fd.eastus.azurecontainerapps.io/healthz'

$Unauthorized = curl.exe -sS -o NUL -w '%{http_code}' `
  -X POST -H 'Content-Type: application/json' -d '{}' $Endpoint
if ($Unauthorized -ne '401') { throw "Unauthenticated MCP returned $Unauthorized" }

$Smoke = .\.venv\Scripts\python.exe .\tests\smoke_http.py $Endpoint $Token |
  ConvertFrom-Json
if ($Smoke.tool_count -ne 29 -or $Smoke.server_version -ne '1.1.1' -or
    -not $Smoke.engine_hash_valid) {
  throw "Remote capability smoke failed: $($Smoke | ConvertTo-Json -Compress)"
}
$RequiredTools = @(
  'initialize_research_graph', 'audit_research_graph',
  'start_scientist_study', 'audit_scientist_project',
  'export_scientist_report'
)
foreach ($Tool in $RequiredTools) {
  if ($Tool -notin $Smoke.tools) { throw "Missing remote tool: $Tool" }
}

$E2EProject = 'azure-e2e-v250-20261026a'
.\.venv\Scripts\python.exe .\tests\smoke_e2e.py `
  $Endpoint $Token $E2EProject
```

Use a new project ID for every retry. The legacy deterministic E2E must report
`search_status=completed`, `audit_valid=true`, `audit_accepted=true` and
`manifest_verified=true`. The 29-tool capability check verifies the new Graph
and Scientist surfaces are exposed; the local server regression remains the
deeper functional test for those surfaces. If a separate remote v2.5 Graph /
Scientist flow is added, preserve both its failed and successful runs rather
than replacing the deterministic E2E.

## 5. Persistence check

After E2E succeeds, restart only the accepted new revision, wait for readiness,
then read the same evidence through MCP:

```powershell
az containerapp revision restart --subscription $Subscription `
  --resource-group $ResourceGroup --name $App --revision $NewRevision

# Wait until the revision is healthy again before this call.
.\.venv\Scripts\python.exe .\tests\smoke_persistence.py `
  $Endpoint $Token $E2EProject
```

Record the returned manifest SHA-256 and file count.

## 6. Rollback

Rollback does not delete evidence or rewrite the old record. In Single revision
mode, create a new revision pinned to the previously captured digest:

```powershell
$RollbackSuffix = 'rollback-v242-20261026'
az containerapp update --subscription $Subscription `
  --resource-group $ResourceGroup --name $App `
  --image $RollbackImage --revision-suffix $RollbackSuffix
```

Then wait for `latestReadyRevisionName` to identify the rollback revision and
rerun health, unauthenticated-401 and `smoke_http.py`. The original known-good
revision is `$RollbackRevision`; the rollback image digest is the authoritative
binary identity.

Rollback triggers include provisioning/readiness failure, image mismatch,
authentication regression, engine hash mismatch, tool count other than 29,
deterministic E2E failure, or persistence failure.

## 7. Evidence to update only after acceptance

After all checks pass, capture without secret values:

```powershell
az containerapp show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App -o yaml
az containerapp revision show --subscription $Subscription `
  --resource-group $ResourceGroup --name $App --revision $NewRevision -o json
az acr repository show --subscription $Subscription `
  --name $RegistryName --image "${Repository}:${Tag}" -o json
```

Write a new v2.5 deployment result or explicitly update the current deployment
record with the new revision, locked digest, engine identity, 29-tool smoke,
E2E project ID and persistence hash. Preserve the v2.4.2 record separately or
retain its complete old values in versioned history. Regenerate and verify
`deployment/release-manifest.json` only after these final records are frozen.
